# kuadrat — design

- **Date:** 2026-08-10
- **Status:** approved design, not yet implemented
- **Owner:** Rifky

## Problem

Deploying an app to a single Linux server still means choosing between two bad options: a
Kubernetes-shaped stack that costs more RAM than the app, or a Docker-based PaaS
(Dokku, Kamal, Coolify, CapRover) that pulls in a daemon and a second supervisor alongside
systemd.

Podman Quadlet removes the daemon — containers become native systemd units — but nothing
wraps it in a deployment loop. There is no "git repo to running service with TLS" path on
Quadlet, no unified place to see status and logs, and no agent-operable interface.

kuadrat fills that gap: a single-host deployment daemon that treats Quadlet as the runtime
and systemd as the supervisor.

## Scope

### v1

- **Deploy loop** — repo to running service with TLS, with rollback on failure
- **Secrets** — `podman secret` management, referenced by name from a spec
- **Logs** — journald reads scoped to a unit
- **Web UI** — status, deploy progress, logs
- **MCP surface** — agent-operable: diagnose failures, natural-language deploys, config authoring
- **Event stream** — typed, subscribable; the integration point for all three surfaces

### Non-goals for v1

- Multi-host / fleet orchestration (the core is built to allow it later; see Architecture)
- Zero-downtime blue/green deploys (in-place replace in v1)
- Webhook receiver / push-to-deploy (deploys are explicitly triggered)
- Notification delivery — kuadrat emits events; subscribers deliver
- Metrics, backups, autoscaling
- Autonomous agent action — the agent proposes, a human approves

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Audience | Own fleet first, public later | Keeps maintenance burden sane; forces a clean boundary anyway |
| Topology | Single-host core, fleet later | Core stays transport-agnostic so a fleet driver is additive |
| Interface | Web UI + agent (MCP), co-equal clients | Both are clients of one API; API is the real product |
| Structure | Library-first: `core` crate + thin binaries | Four consumers (daemon, CLI, UI, MCP) justify the boundary |
| Coupling | Standalone; postlab is an optional client | Dependencies point one way; deleting any client changes nothing |
| Source of truth | Spec in SQLite; unit files are derived | Makes rollback a DB operation and drift detection free |
| Replace strategy | In-place for v1 | Low-memory hosts; blue/green is additive later |
| Agent role | Advisory (diagnose, NL deploy, config authoring) | No unsupervised root action on servers |
| Network exposure | Loopback / unix socket only; no auth code in v1 | Reachability is the operator's job (SSH tunnel, VPN); shipping an auth stack is the larger risk |

## Architecture

```
clients — all optional, none required
  browser (web UI)  ·  cli  ·  agent via MCP  ·  postlab
                         │
                         │  HTTP / MCP / unix socket
                         ▼
daemon binary — the only networked component
  axum HTTP API · embedded htmx UI · MCP server · event bus
                         │
                         │  direct calls
                         ▼
core crate — transport-agnostic, host-local
  spec · workloads · gateway · deploy · secrets · logs · events
```

**The invariant that makes this work:** `core` never opens a socket and never knows about
hosts. It manipulates the local filesystem, systemd, and podman. Everything network-facing —
HTTP, MCP, auth — lives in the daemon.

That invariant is what preserves the fleet option. A fleet driver is another consumer of
`core`, executing through a remote executor over SSH. **If `core` ever grows a `host: &str`
parameter, this design has failed.**

**Network exposure.** The daemon binds a unix socket and loopback only. It ships no login, no
session handling, and no TLS of its own; reaching the UI from elsewhere is the operator's
job via an SSH tunnel or VPN. This is a deliberate v1 boundary — a self-rolled auth stack on a
root-privileged daemon is a larger risk than not exposing the port. Binding a public interface
is not supported in v1, and the daemon refuses to start if configured to.

**Repo placement:** independent repo, tracked as a submodule at the devbox root alongside the
other product repos, with a `docs/INDEX.md` row and a capability card.

## Components

### `core` crate

| Module | Responsibility | Key interface |
|---|---|---|
| `spec` | Serializable workload description — image, ports, volumes, env, secret names, limits, route | `WorkloadSpec` |
| `workloads` | Render spec to a `.container` unit, write, `daemon-reload`, start/stop/remove, status | `apply`, `remove`, `status` |
| `gateway` | Caddy route CRUD (domain to port, automatic TLS) | `add_route`, `remove_route` |
| `deploy` | Orchestrates the loop as an explicit state machine | `run(&DeployRequest) -> DeployOutcome` |
| `secrets` | `podman secret` wrapper; emits `Secret=` lines into units | `set`, `list`, `remove` |
| `logs` | Journald reader scoped to a unit | `tail`, `search` |
| `events` | Typed event stream every operation emits | `Event` + subscribe |

All host interaction (`podman`, `systemctl`, Caddy) goes through an **executor trait**. The
local implementation shells out; a fake implementation backs the tests; a future remote
implementation would run over SSH.

### Binaries

- **`daemon`** — axum HTTP API, embedded htmx UI, MCP server, event bus. One systemd unit.
- **`cli`** — same operations headless. The fallback interface and what the installer drives.

Both are orchestration only; logic lives in `core`.

### Extraction note

postlab's `core/workloads/mod.rs` (~1,040 lines) is the starting point for `workloads` — the
logic is proven and should be moved, not rewritten. Split it on the way in: `spec.rs`,
`render.rs`, `apply.rs`, `query.rs`. Its injectable `Paths` struct must be preserved; it is
what makes filesystem tests possible. `core/gateway/caddy.rs` (~245 lines) moves largely
as-is. `core/deploy/` (~174 lines) is early and is effectively rewritten as the state machine.

## Data flow

Deploys are explicitly triggered — `kuadrat deploy <app>` via CLI, API, or agent.

```
Detect → Build → Secrets → Apply → Route → Healthcheck → Done
   └────────┴────────┴────────┴───────┴──────────┘
                   on failure → RolledBack
```

| Stage | Does | Fails when |
|---|---|---|
| Detect | Read repo at ref, identify stack (Containerfile, Node, Rust, Python, static) into a `BuildPlan` | No recognizable stack |
| Build | `podman build`, image tagged with the git commit SHA | Build error |
| Secrets | Verify every referenced secret exists | Missing secret |
| Apply | Render unit, write, `daemon-reload`, start | Invalid unit, start failure |
| Route | Caddy route, automatic TLS | Caddy rejects config, ACME failure |
| Healthcheck | Poll unit health until healthy or timeout | Timeout, unhealthy |

**Stage ordering is a correctness decision.** Secrets are verified before Apply so a missing
credential fails while the old version is still running. Route follows Apply so traffic is
never sent to a service that is not up. Healthcheck gates `Done` — a started unit is not a
successful deploy.

### State

| Store | Holds | Note |
|---|---|---|
| SQLite | Specs, deploy history, event log, secret **names** | Source of truth |
| `/etc/containers/systemd` | Generated `.container` units | Derived; kuadrat owns and may overwrite |
| `podman secret` | Secret **values** | Never in SQLite, never in the event log |
| Caddy | Routes | Derived from spec |

### Event stream

Every transition emits `Event { deploy_id, stage, status, detail }`, consumed three ways from
one source:

- **Web UI** — SSE, live progress
- **MCP** — the agent reads the failed stage plus its error, rather than scraping logs
- **External subscribers** — outbound webhook and/or an exec hook on failure

kuadrat has no notification providers and no chat integrations. Dedupe, rate-limiting, and
delivery belong to the subscriber.

## Error handling

### Per-stage compensation

| Fails at | Compensating action | Old version |
|---|---|---|
| Detect / Build | None needed | Still serving |
| Secrets | None needed | Still serving |
| Apply | Restore previous unit, `daemon-reload`, start | Restored |
| Route | Revert route to previous target | Still serving |
| Healthcheck | Revert route, restore previous unit | Restored |

Rollback re-applies the previous spec from SQLite through the same Apply → Route →
Healthcheck path. No special-case code path, and rollback is covered by the same tests as a
normal deploy.

### Designed-for failure modes

- **Concurrent deploys** — per-app lock in SQLite. A second deploy of the same app is
  rejected, not queued.
- **Crash mid-deploy** — on daemon start, any deploy left `in_progress` is reconciled: compare
  the running unit against the last `Done` spec, then finish or roll back.
- **Drift** — a hand-edited unit is detected by regenerating from the spec and comparing.
  Reported, never silently overwritten.
- **Rollback fails** — stop, mark the deploy `Failed`, emit an event, leave the host as-is.
  Never retry automatically.

Errors are a typed enum tagged with the stage they occurred in. That tagging is what makes the
agent's diagnose role tractable.

## Testing

1. **Render tests (golden files)** — `WorkloadSpec` to `.container` text against checked-in
   expected output. No I/O. Catches the most likely bug class (Quadlet syntax) in milliseconds.
   Every spec feature gets a case.
2. **Filesystem tests against a temp root** — using the injectable `Paths` struct carried over
   from postlab.
3. **State machine tests with a faked executor** — force a failure at each stage, assert the
   compensation ran. The most important layer: these are the paths that cannot be safely
   tested in production.
4. **Integration** — one real podman + systemd environment in CI, deploying a trivial sample
   app end to end, plus one forced-failure run that must roll back. Kept to a handful of cases;
   it exists to prove the fakes are honest.

Deliberately not deeply tested: the web UI beyond a route-render smoke test, and the MCP
surface beyond schema validity. Both are thin clients over `core`.

**Gate:** `make check && make test` must pass with zero warnings before any task is done.

## Prior art

| Project | Overlap | Gap it leaves |
|---|---|---|
| [quadit](https://crates.io/crates/quadit) | GitOps deploy of Quadlet units, Rust | No web UI, gateway/TLS, secrets, or agent surface. Closest prior art — read before implementing. |
| [quadletman](https://github.com/mikkovihonen/quadletman) | Web UI managing Quadlet units | No deploy loop, no gateway, no agent |
| Cockpit / RHEL web console | Quadlet management in a web console | Single host, no deploy, no agent. Vendor-backed — assume it grows. |
| [podlet](https://github.com/containers/podlet) | Compose and `podman run` to Quadlet conversion | One-shot by design; not a lifecycle tool |
| Dokku, Kamal, Coolify, CapRover | Full PaaS, git deploy, TLS | Docker-only; none compose with Podman or systemd-native units |

The unoccupied combination is **deploy loop + gateway/TLS + agent surface on Quadlet**.

## Implementation sequence

v1 is too large for a single implementation plan. Four phases, each independently useful and
each getting its own plan:

1. **`core` foundation** — repo, workspace, `spec`, executor trait, `workloads` extracted and
   split, render golden tests, filesystem tests. Done when a spec can be applied and removed on
   a real host via a test binary.
2. **Deploy state machine** — `deploy`, `gateway`, `secrets`, event types, per-stage
   compensation, concurrency lock, crash reconciliation, faked-executor tests. Done when
   `kuadrat deploy` takes a repo to a running service with TLS and rolls back on failure.
3. **Daemon and surfaces** — HTTP API, SSE, embedded htmx UI, `logs`, outbound webhook.
   Done when a deploy can be run and watched from a browser.
4. **MCP surface** — tool definitions for diagnose, deploy, and config authoring over the
   existing API. Done when an agent can diagnose a failed deploy end to end.

Phase 2 is the wedge; phases 3 and 4 are surfaces over work already done. If the project
stalls, it should stall after phase 2 with something genuinely useful.

## Deferred

- Fleet driver (remote executor over SSH)
- Blue/green deploys
- Webhook receiver for push-to-deploy
- Metrics and backups
- Migrating postlab into the devbox submodule convention
